## ADR-003: Localization approach for the Docs & Board Viewer

**Date:** 2026-08-20
**Status:** accepted
**Stale after:**
**Journal:**
**Task:** [TASK-002](/tasks/TASK-002_multilingual-viewer.md)

### Context

The viewer (`tool/docs-viewer.html`, TASK-001) hardcoded its ~30 UI strings in Hungarian. The repository is being published publicly in English, so the viewer needed an English display layer — while keeping Hungarian available for the primary user, switchable at runtime.

### Question

How should the viewer's display language be implemented, and which language should be the default?

### Alternatives

**Option A: In-file `I18N` dictionary + `data-i18n` attributes**
- Description: A plain dictionary with a `t()` lookup, `data-i18n` attributes on static elements, and a `setLang()` re-render entry point.
- Advantage: No build step, no network dependency; stays a portable single file; trivially extensible with further languages.
- Disadvantage: Manual key management; per-language format strings needed for plurals.

**Option B: External library or build step**
- Description: i18next-style library or a compile-time string extraction.
- Advantage: Richer plural/format rules, tooling.
- Disadvantage: Violates the viewer's zero-dependency, single-file, server-less constraint.

### Decision

**(a) In-file `I18N` dictionary** with `t(key, vars)`, `data-i18n` / `data-i18n-placeholder` / `data-i18n-html` attributes, and `setLang()` that re-applies static strings, re-renders JS strings and persists the choice in `localStorage` (try/catch-guarded, safe under `file://`). **Default language: English** — the repo is public and English-first; Hungarian remains available and is persisted once chosen.

### Rationale

Consistent with the viewer's zero-dependency, single-file design (ADR-002 precedent). A build step would defeat the tool's portability goal. English as the default matches the public, English-first repository; `localStorage` persistence keeps Hungarian users on their choice.

### Consequences

- UI chrome and all JS-rendered strings are localized; canonical data values (board columns, priorities, type names) stay English in both languages.
- The language `<select>` lives in the top-right corner of the header (`EN English` / `HU Magyar`).

### Review Criteria

Revisit if the bundle itself ever becomes bilingual (then canonical data values may need localization too).

## ADR-001: Board data source in the Docs & Board Viewer kanban view

**Date:** 2026-08-20
**Status:** accepted
**Stale after:**
**Journal:**
**Task:** [TASK-001](/tasks/TASK-001_standalone-docs-board-viewer.md)

### Context

The kanban view of `tool/docs-viewer.html` was built as a continuation of `test/board-viewer.html`, which parsed the generated `_docs/BOARD.md`. The viewer grew into a general docs viewer; the question arose whether the board should read the generated BOARD.md or the TASK files.

### Question

Should the kanban view read the generated `BOARD.md`, or the TASK files directly?

### Alternatives

**Option A: BOARD.md parse**
- Description: The board is built from the `_docs/BOARD.md` generated by `/board-sync`, as in the previous iteration.
- Advantage: Simple, no client-side reproduction of the board logic.
- Disadvantage: The viewer depends on whether `/board-sync` has run; the generated view would be a second source of truth.

**Option B: Direct reading of TASK files**
- Description: The board is built directly from the TASK files' frontmatter and "Approach / Plan" checklist, reproducing the board-sync logic client-side.
- Advantage: The TASK frontmatter is the primary source of truth; it does not depend on `/board-sync` having run.
- Disadvantage: A client-side copy of the board-sync logic (must be kept in sync).

### Decision

**(c) Both, with a switch** — the board is built primarily from TASK files, with the BOARD.md-parse fallback mode retained.

### Rationale

The TASK files' frontmatter (`status`, `priority`, `complexity`, `verified`) is the primary source of truth; the viewer thus does not introduce a second source of truth and works even if `/board-sync` has not yet run. The BOARD.md fallback remains useful for those who want to quickly check the generated view.

### Consequences

- The "Board source" switch toggles between the two modes; when a single BOARD.md is loaded it automatically switches to BOARD.md mode, when a full folder (with tasks) is loaded it stays TASK-based.

### Review Criteria

If the board-sync logic changes significantly, the viewer's client-side reproduction must be kept in sync as well.

## ADR-002: Folder loading method in the Docs & Board Viewer

**Date:** 2026-08-20
**Status:** accepted
**Stale after:**
**Journal:**
**Task:** [TASK-001](/tasks/TASK-001_standalone-docs-board-viewer.md)

### Context

The viewer must be able to load a full `_docs/` folder via drag&drop or file picker. Several browser APIs are available for folder-level file reading.

### Question

Which browser API should be used for folder-level file reading?

### Alternatives

**Option A: File System Access API (`showDirectoryPicker()`)**
- Description: The modern, promise-based Chromium API with a folder picker.
- Advantage: Clean, native folder handling.
- Disadvantage: Chromium-only, narrower browser support; does not solve drag&drop.

**Option B: `webkitGetAsEntry()` + `webkitdirectory` input**
- Description: Recursive traversal with `DataTransferItem.webkitGetAsEntry()` on drag&drop, `<input type="file" webkitdirectory>` on click.
- Advantage: Older, more widely supported (Chrome, Edge, Firefox); retains the existing drag&drop UX with minimal additions.
- Disadvantage: Relies on `webkit`-prefixed APIs; in Firefox, drag&drop folder contents cannot be read (though the `webkitdirectory` input works).

### Decision

**(b) A combination of `webkitGetAsEntry()` + `webkitdirectory`.**

### Rationale

`showDirectoryPicker()` is Chromium-only, with narrower compatibility; the `webkitGetAsEntry()`/`webkitdirectory` pair is more widely supported, and we also built in a fallback to `dataTransfer.files` for drops to handle cross-browser differences.

### Consequences

- Drag&drop reads the full folder structure in all WebKit/Chromium browsers; in Firefox, folder drops fall back to the flat `dataTransfer.files` list, where the `webkitdirectory` input provides the full paths.
